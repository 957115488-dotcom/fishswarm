# 鱼群产品设计文档

日期：2026-06-08
产品名：鱼群
版本：v0.2

## 1. 重新定位

鱼群不是一个只服务某类具体项目的应用，而是一个多 Agent 协同办公工厂。

它的核心目标是提供一套可以持续扩展的 Agent 组织、入职、协作、派工、执行、评审、交付框架。后续用户只需要把特定角色的 Agent 配置进这个工厂，例如产品经理、架构师、前端工程师、财务分析师、法务顾问、运营策划、投放专家、客服主管，鱼群就能围绕不同业务目标组建临时团队并完成项目。

一句话定位：

> 鱼群是一个可配置的多 Agent 协同办公工厂，让不同 AI 员工入职、组队、协作并交付项目。

英文定位：

> FishSwarm is a configurable multi-agent work factory where AI workers can be onboarded, organized, coordinated, and assigned to deliver projects.

## 2. 核心隐喻

鱼群不是“一个聊天机器人”，也不是“几个 Agent 聊天窗口”。

鱼群更像一个组织系统：

1. 工厂：提供制度、流程、岗位、权限、任务流和交付标准。
2. 员工：每个 Agent 是可入职、可培训、可考核、可替换的工作角色。
3. 项目：用户派发的目标会被工厂拆解成可执行任务。
4. 班组：不同 Agent 根据项目需要临时组队。
5. 流水线：任务按照依赖、阶段和质量门禁推进。
6. 管理层：协调 Agent 负责计划、分派、冲突解决和交付汇总。

这个隐喻比“多 Agent 应用”更大：鱼群的价值不是某个 Agent 多聪明，而是它能不断吸纳新角色，并让这些角色按统一规则协同工作。

## 3. 产品目标

### 3.1 长期目标

成为一个通用的 AI 协作组织运行框架。用户可以为不同业务场景搭建自己的 Agent 工厂，例如：

1. 软件开发工厂。
2. 市场研究工厂。
3. 内容生产工厂。
4. 销售运营工厂。
5. 客服支持工厂。
6. 财务分析工厂。
7. 法务合规工厂。
8. 企业内部自动化办公工厂。

### 3.2 第一阶段目标

第一阶段不追求覆盖所有行业，而是先把“工厂底座”做出来：

1. 能创建 Agent 员工。
2. 能定义岗位、能力、工具权限和工作规范。
3. 能把多个 Agent 组成一个团队。
4. 能把用户项目拆成任务。
5. 能把任务派发给合适的 Agent。
6. 能追踪执行过程、产出物和质量评审。
7. 能沉淀一套可复用的项目模板和组织模板。

软件开发项目可以作为第一个演示工厂，但它不是鱼群的终点。

## 4. 核心用户

### 4.1 工厂创建者

这类用户负责搭建某类业务工厂。他们关心：

1. 如何创建角色。
2. 如何配置角色能力。
3. 如何设计工作流程。
4. 如何设置工具权限。
5. 如何定义交付标准。

典型用户：

1. 创业者。
2. 工作室负责人。
3. 企业数字化负责人。
4. AI 自动化顾问。
5. 软件团队负责人。

### 4.2 项目派发者

这类用户只关心把目标交给鱼群，然后看到结果。他们关心：

1. 如何描述需求。
2. 什么时候需要我确认。
3. 当前进度如何。
4. 最终交付物是什么。
5. 质量是否可靠。

### 4.3 Agent 设计者

这类用户负责编写和维护 Agent 员工。他们关心：

1. 角色提示词。
2. 输入输出格式。
3. 可用工具。
4. 记忆与知识库。
5. 评价标准。
6. 与其他 Agent 的交接协议。

## 5. 产品分层

鱼群应该分成三层，而不是直接做某个垂直应用。

### 5.1 工厂底座层

负责通用能力：

1. 用户和工作区。
2. Agent 注册与管理。
3. 角色、权限和工具配置。
4. 项目、任务和状态流转。
5. 编排器。
6. 记忆和上下文管理。
7. 产物管理。
8. 审核和质量门禁。
9. 日志和追踪。

### 5.2 工厂模板层

负责把底座能力组合成特定业务工厂。

示例模板：

1. 软件开发工厂。
2. 研究分析工厂。
3. 内容营销工厂。
4. 电商运营工厂。
5. 客户支持工厂。

每个工厂模板包含：

1. 默认组织结构。
2. 默认 Agent 员工。
3. 默认项目流程。
4. 默认任务类型。
5. 默认质量门禁。
6. 默认交付物类型。

### 5.3 项目执行层

负责具体项目运行：

1. 接收项目目标。
2. 选择或创建工厂模板。
3. 组建项目团队。
4. 拆解任务。
5. 执行任务。
6. 评审产物。
7. 请求用户确认。
8. 生成最终交付物。

## 6. 核心概念模型

### 6.1 Workspace

工作区是用户或团队拥有的组织空间。

包含：

1. 工厂模板。
2. Agent 员工。
3. 项目。
4. 工具连接。
5. 知识库。
6. 交付物。

### 6.2 Factory

工厂是一套可复用的业务协作系统。

字段示例：

1. 名称。
2. 描述。
3. 适用项目类型。
4. 默认组织结构。
5. 默认流程。
6. 默认质量标准。
7. 可用工具集合。

### 6.3 Agent Worker

Agent Worker 是工厂里的 AI 员工。

一个员工不只是一个 prompt，而是一份完整的岗位档案：

1. 姓名。
2. 岗位。
3. 职责。
4. 能力描述。
5. 输入要求。
6. 输出格式。
7. 工具权限。
8. 可访问知识库。
9. 工作准则。
10. 评价标准。
11. 交接协议。

### 6.4 Team

Team 是为某个项目临时组建的 Agent 团队。

一个 Team 可以来自某个工厂模板，也可以由用户手动添加和替换成员。

### 6.5 Project

Project 是用户派发给鱼群的目标。

项目应该与具体行业解耦。它可以是：

1. 开发一个 SaaS MVP。
2. 产出一份竞品分析报告。
3. 策划一场营销活动。
4. 搭建一个自动化工作流。
5. 整理一套客服知识库。

### 6.6 Task

Task 是项目拆解后的最小执行单元。

任务包含：

1. 目标。
2. 输入。
3. 输出。
4. 负责人。
5. 协作者。
6. 依赖关系。
7. 验收标准。
8. 当前状态。

### 6.7 Artifact

Artifact 是 Agent 工作产生的产物。

可以是：

1. 文档。
2. 代码。
3. 表格。
4. 图片。
5. 报告。
6. 流程图。
7. 数据集。
8. 决策记录。

### 6.8 Tool

Tool 是 Agent 能调用的外部能力。

例如：

1. 搜索。
2. 浏览器。
3. 代码执行。
4. 文件读写。
5. 数据库。
6. GitHub。
7. 飞书。
8. 邮件。
9. 表格。
10. 内部 API。

## 7. Agent 入职机制

“入职”是鱼群最重要的产品动作之一。

用户不应该只是填写一段 prompt，而是完成一份员工入职档案。

### 7.1 入职流程

1. 选择岗位类型。
2. 填写岗位职责。
3. 定义能力边界。
4. 绑定工具权限。
5. 绑定知识库。
6. 定义输入输出格式。
7. 定义协作对象。
8. 定义验收标准。
9. 运行试用任务。
10. 保存为正式员工。

### 7.2 Agent 员工档案

建议字段：

1. `name`：员工名称。
2. `role`：岗位。
3. `mission`：核心使命。
4. `responsibilities`：职责清单。
5. `skills`：能力标签。
6. `constraints`：不能做什么。
7. `tools`：可用工具。
8. `knowledge_sources`：知识来源。
9. `input_schema`：输入结构。
10. `output_schema`：输出结构。
11. `handoff_rules`：交接规则。
12. `review_criteria`：评价标准。
13. `escalation_rules`：何时升级给用户或管理 Agent。

### 7.3 试用期

新入职 Agent 可以先进入试用状态。

试用期内：

1. 只能执行低风险任务。
2. 所有输出需要评审 Agent 复核。
3. 系统记录成功率、返工率和用户满意度。
4. 达标后转为正式员工。

这个设计能让鱼群像真实组织一样成长，而不是堆 prompt。

## 8. 组织与协作机制

### 8.1 管理角色

每个工厂至少需要一个管理 Agent。

常见管理角色：

1. Factory Manager：负责工厂级规则、人员和流程。
2. Project Manager：负责具体项目计划、派工和进度。
3. Reviewer：负责质量评审。
4. Dispatcher：负责根据任务匹配 Agent。

第一版可以合并为一个 Orchestrator，但产品概念上应该保留这些角色。

### 8.2 协作协议

Agent 之间不能只靠自由对话协作，需要结构化协议。

每次交接至少包含：

1. 上游任务目标。
2. 已完成内容。
3. 关键决策。
4. 未解决问题。
5. 下游需要使用的产物。
6. 验收标准。

### 8.3 冲突解决

当 Agent 之间意见冲突时，系统应该按优先级处理：

1. 先交给 Review Agent 判断。
2. 再交给 Project Manager Agent 仲裁。
3. 仍无法确定时请求用户决策。

### 8.4 记忆机制

鱼群需要至少三类记忆：

1. 项目记忆：当前项目的需求、决策和产物。
2. 员工记忆：某个 Agent 的长期偏好、经验和历史表现。
3. 工厂记忆：某类项目的流程模板、最佳实践和常见问题。

## 9. 项目执行流程

鱼群的通用执行流程应该与行业无关。

### 9.1 接单

用户提交目标，系统判断：

1. 适合哪个工厂。
2. 需要哪些 Agent。
3. 是否缺少关键信息。
4. 是否需要用户先补充材料。

### 9.2 立项

管理 Agent 生成：

1. 项目目标。
2. 成功标准。
3. 约束条件。
4. 初始风险。
5. 推荐团队。

### 9.3 组队

系统从员工池中选择 Agent。

选择依据：

1. 岗位匹配。
2. 能力匹配。
3. 工具权限。
4. 历史表现。
5. 当前负载。

### 9.4 拆解

管理 Agent 生成任务图。

任务图包含：

1. 阶段。
2. 任务。
3. 依赖。
4. 负责人。
5. 交付物。
6. 验收标准。

### 9.5 执行

Agent 按任务图执行。

系统负责：

1. 准备上下文。
2. 调用模型和工具。
3. 保存日志。
4. 保存产物。
5. 更新状态。
6. 触发下游任务。

### 9.6 评审

评审可以发生在任务级、阶段级和项目级。

评审内容：

1. 是否满足验收标准。
2. 是否遗漏需求。
3. 是否违反约束。
4. 是否需要返工。
5. 是否需要用户确认。

### 9.7 交付

最终交付包括：

1. 主要产物。
2. 过程记录。
3. 决策记录。
4. 使用说明。
5. 已知问题。
6. 下一步建议。

## 10. MVP 功能范围

第一版的 MVP 应该验证“工厂底座”，而不是验证某个行业应用。

### 10.1 必须有

1. Workspace 创建。
2. Agent 员工创建。
3. Agent 员工档案配置。
4. 工厂模板创建。
5. 项目创建。
6. 根据项目选择工厂模板。
7. 自动组队。
8. 自动任务拆解。
9. 任务看板。
10. Agent 执行日志。
11. 产物管理。
12. 人工确认节点。
13. 简单评审流程。

### 10.2 第一批内置模板

建议内置两个模板，而不是只做一个：

1. 软件开发工厂。
2. 研究分析工厂。

原因：

1. 软件开发能展示复杂协作和真实交付。
2. 研究分析能证明鱼群不是只能写代码。
3. 两个模板足以倒逼底座抽象，而不会过早泛化到失控。

### 10.3 暂不做

1. Agent 公开市场。
2. 复杂企业权限。
3. 完整计费系统。
4. 完全自动部署。
5. 无限制工具调用。
6. 跨组织员工共享。

## 11. 软件开发工厂示例

软件开发工厂只是鱼群的第一个模板。

默认员工：

3. 前端工程师。
4. 后端工程师。

1. 需求澄清。

3. 技术方案。

## 14. 技术架构

### 14.1 前端

建议：

1. Next.js。
2. React。
3. Tailwind CSS。
4. Zustand 或 Jotai 管理局部状态。
5. React Flow 展示任务图和组织图。

### 14.2 后端

建议：

1. NestJS 或 Next.js API Routes。
2. PostgreSQL。
3. Prisma。
4. Redis。
5. BullMQ。

如果目标是快速原型，可以先用 Next.js 全栈；如果目标是长期做框架，NestJS 的模块边界会更舒服。

### 14.3 Agent Runtime

Agent Runtime 应该独立于具体业务工厂。

能力：

1. 加载 Agent 档案。
2. 加载任务上下文。
3. 根据权限注入工具。
4. 调用模型。
5. 校验结构化输出。
6. 保存运行记录。
7. 触发评审或下游任务。

### 14.4 Orchestrator

Orchestrator 是鱼群的核心。

职责：

1. 选择工厂。
2. 组建团队。
3. 生成任务图。
4. 匹配任务和 Agent。
5. 控制状态流转。
6. 处理失败和重试。
7. 触发人工确认。
8. 汇总交付物。

### 14.5 Tool Gateway

所有 Agent 工具调用都应经过 Tool Gateway。

原因：

1. 控制权限。
2. 记录调用。
3. 限制风险。
4. 统一错误处理。
5. 方便后续接入更多工具。

4. `running`
5. `reviewing`
6. `needs_rework`
7. `blocked`
8. `done`
9. `cancelled`

## 17. 质量与安全边界

鱼群是一个能调用工具、生成产物、影响业务流程的系统，所以从第一版就要有边界。

### 17.1 权限边界

1. Agent 默认无工具权限。
2. 工具权限按岗位授予。
3. 高风险工具需要用户确认。
4. 所有工具调用必须记录。

### 17.2 输出边界

1. 关键产物需要结构化输出。
2. 重要结论需要来源或依据。
3. 无法确定时必须标记不确定性。
4. 不允许把推测伪装成事实。

### 17.3 人工确认

以下动作应触发用户确认：

1. 修改外部系统。
2. 发送消息。
3. 花费额度。
4. 删除文件。
5. 发布内容。
6. 确认最终交付。

## 18. MVP 推荐路线

### Phase 1：工厂原型

目标：证明“可配置 Agent 工厂”这个概念。

功能：

1. 创建工厂。
2. 创建 Agent 员工。
3. 把员工加入工厂。
4. 创建项目。
5. 自动生成项目团队。
6. 自动生成任务图。
7. 模拟执行日志和产物。

### Phase 2：真实执行

目标：让 Agent 真正执行部分任务。

功能：

1. Agent Runtime。
2. Orchestrator。
3. 队列执行。
4. 工具网关。
5. 结构化输出校验。
6. 任务评审。

### Phase 3：模板生态

目标：沉淀多个可复用工厂。

功能：

1. 软件开发工厂。
2. 研究分析工厂。
3. 内容生产工厂。
4. 工厂模板复制。
5. Agent 员工复制。
6. 项目模板。

### Phase 4：组织化协同

目标：让鱼群成为团队级平台。

功能：

1. 多用户工作区。
2. 权限管理。
3. 工具集成。
4. 成本统计。
5. Agent 表现分析。
6. 工厂版本管理。

## 19. 关键差异化

鱼群的差异化不在于“有很多 Agent”，而在于它把 Agent 当成员工管理。

核心差异：

1. Agent 可入职，而不是只配置 prompt。
2. 工厂可复用，而不是每次从零聊天。
3. 项目可派发，而不是用户手动推进每一步。
4. 流程可编排，而不是 Agent 自由散聊。
5. 工具可管控，而不是无限制调用。
6. 产物可追踪，而不是散落在对话里。
7. 质量可评审，而不是一次性生成结果。

## 20. 下一步建议

下一步不应该先写某个垂直业务功能，而应该先做“鱼群工厂底座”的产品原型。

建议第一个可点击原型包含：

1. 工厂列表。
2. 创建工厂。
3. 员工池。
4. Agent 入职表单。
5. 工厂组织结构。
6. 项目派发表单。
7. 自动组队结果。
8. 任务图。
9. 执行看板。
10. 产物中心。

其中“软件开发工厂”和“研究分析工厂”作为两个内置示例模板，用来验证底座足够通用。

真正要先打磨的是这句话：

> 我不是在雇一个 AI 助手，我是在搭建一个会工作的 AI 组织。
